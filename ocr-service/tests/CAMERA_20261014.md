# Actual JPEG / HEIC camera benchmark

The two supplied PDFs are the reference, checked visually because they contain
scanned images rather than selectable text. Ground-truth values and PDF SHA256
hashes are in `camera-ground-truth.json`. No source images, numerical answers or
company identities are hardcoded into OCR/parser logic.

The four original 4080×3060 camera files match 46/48 printed fields (95.8%);
all 36 main order fields match. Comparison normalizes NFKC, whitespace and
equivalent corporate abbreviations. Unprinted postal code/phone fields are
excluded from the score, and remain blank. Both Masuda photos still misread
part of `ドブ漬け酸洗い処理`; the process field is explicitly marked for review.
The JPEG's recovered unit-price header is also marked for review; its 6000
value was read from the corresponding image cell, never calculated from totals.

A controlled before/after pass using the same warmed engines/image pixels:

| Masuda | 15.758s | 12.555s |

An initial separate-process baseline took 14.564s/14.375s on the JPEGs but missed
most Masuda fields and Shinwa dates/name. HEIC was rejected as unsupported.
Separate process/model initialization and CPU load make those initial times
different from the paired measurement. All measured final requests were below
one minute locally. Upload, network, queue wait and model startup are excluded;
these measurements do not guarantee every tablet/network completes in a minute.

The same six real files were also executed in the active service's `.venv`
(RapidOCR 1.4.4 / ONNX Runtime 1.30.0), with identical matching-field outcomes.
Its full decode + OCR timings were JPEG 29.856s / 19.642s, HEIC 26.527s /
19.274s, PDFs 16.673s / 15.380s. These independently measured timings and raw
lines are retained in `camera-runtime-results.json`; they include image decode
but exclude the separately reported model initialization and upload/queue wait.

A 90-degree rotation plus JPEG quality 80 of the supplied Shinwa photo also
matches all 12 printed fields (24.924s), including dates with browser chrome
remaining above the paper. This derived input is an additional stress case,
not a fifth original photo. Raw lines, parsed fields and timings are recorded in
`camera-20261014-results.json` / `camera-20261014-summary.json`; parser regression
fixtures retain the original OCR observations, including unresolved errors.

Changes: full-frame HEIC decode with orientation metadata. HEIC crop previews use
a decode-only JPEG conversion; OCR starts only after confirming the crop. Camera preparation
closes table-rule holes before locating the sheet, trims sparse toolbar rows,
deskews and resamples display moire. Both recognizers share one detector; known
headers/Latin codes avoid duplicate recognition. At most six weak text crops get
a contrast/rule-cleaning retry, and orientation checks at most four crops in each
direction. Company/header selection preserves complete multilingual readings
over damaged Japanese alternatives. Parser repairs only unambiguous short header
errors and keeps uncertain values marked for review.

To repeat inference locally (no documents leave the machine):

```powershell
python ocr-service/tests/benchmark_camera.py --output camera-benchmark.json <photo paths> <PDF paths>
```

Install the updated `ocr-service/requirements.txt` and restart the OCR service;
the Docker image includes HEIF support and the async job module. Existing PDF
extraction and malformed/oversized-file handling remain covered by tests.
